# 古籍制版 · 字模工位管理

几册古籍陆续送到同一制版工位、共用外字字模。本服务管理分册用字与优先字库清单，
在每次“交印”时算出工位上字模的**增减单**：哪些字模要补备、哪些可以撤下。

## 业务规则

1. 上传**按优先顺序排列的字库清单**（CSV：`字库,版次,字模号,字`），文件顺序即优先级。
   每次**成功上传**都整体存为一个不可变的清单版本，指针切到最新版本；
   上传失败（解析失败、字模号恒定校验失败、保存失败）指针不动，继续使用上一份清单。
2. 上传**分册用字表**（CSV：`字`，每格可多字、可无表头）。
3. **一笔交印只使用一份完整清单**：进入交印事务即锁定当前清单版本，
   每个字只在该清单内取**第一个收录它的字库**中的字模，按 **(字库, 版次, 字模号)** 识别字模；
   清单内缺字（无后备库收录）则**整笔拒绝交印**，各册仍沿用原清单、不产生新单。
4. 交印一册时**只更新该册**选用的字模；其余册沿用各自上次交印的清单（从未交印的册不参与共需）。
   已交印册的字模固定在交印当时的清单版本上，重传清单不会改写历史交印与历史单据。
5. 比对交印前后**各册共需字模的并集**，生成增减单；只有最后一个使用某字模的册撤下它时，才出现“减”项。
6. **并发交印按生效次序逐单出单**：上传与交印共用进程内互斥锁 + SQLite `BEGIN IMMEDIATE`/WAL/忙等待双重保证，
   每单提交前后都校验并集与各册 active 清单一致，不一致即回滚报错。
7. **重复确认复用原单**：
   - 带 `Idempotency-Key` 请求头：同键永远返回同一单；
   - 不带键：同册、同用字、解析目标与当前已交印清单完全相同（无变化）时，复用该册最近一单；
   - 按单号 `GET /api/orders/{单号}` 可原样重取，`.../download` 下载 CSV。
8. **缺字或保存失败时整笔回滚**，各册仍沿用原清单，不产生新单。
9. **字模号恒定不变量**：同一字库同一版次内，字模号始终对应同一个字；
   新清单与任一历史版本冲突即整单拒绝（本次上传不生效）。

## 目录

```
app/            FastAPI 应用（database/parsers/service/main）
web/index.html  单页操作界面（上传、交印、重取、下载、状态总览）
samples/        网页与接口可直接使用的样例 CSV（1 份字库清单 + 2 册用字表）
tests/          pytest 端到端测试（10 个用例）
Dockerfile / docker-compose.yml
```

## Docker Compose 启动

```bash
docker compose up --build
# 打开 http://localhost:8000/
# SQLite 数据持久化在命名卷 matrix-data -> /data/matrix.db
```

页面上可直接下载 `/samples/` 下的样例文件，按 ① 字库清单 → ② 用字表 → ③ 交印 的顺序操作。

## 本地运行（无 Docker 时）

```bash
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000
# 测试
pip install -r requirements-dev.txt
pytest -q
```

## HTTP 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/libraries` |  multipart 上传字库清单 CSV；整单校验通过后生成新版本并切换当前清单，失败沿用上一份 |
| POST | `/api/volumes/{册名}/chars` | 上传该册用字表 CSV，全量替换用字 |
| POST | `/api/volumes/{册名}/submit` | 交印并出增减单；只按当前清单版本取字，缺字 422 拒绝；可选 `Idempotency-Key` |
| GET  | `/api/orders?volume=册名` | 按生效次序列出单据（含各单使用的清单版本号） |
| GET  | `/api/orders/{单号}` | 按单号原样重取 JSON |
| GET  | `/api/orders/{单号}/download` | 下载增减单 CSV（带 BOM，Excel 直开） |
| GET  | `/api/state` | 当前清单版本与历史版本、各册用字/已交印字模、共需并集 |
| POST | `/api/reset` | 清空全部数据（演示用） |
| GET  | `/docs` | Swagger 交互文档 |

增减单 JSON 关键字段：`added` / `removed`（共需池层面的增减，含字库/版次/字模号/字）、
`pool_before` / `pool_after`（交印前后共需并集）、`volume_before` / `volume_after`（该册清单）、
`library_list_id`（本单锁定使用的清单版本）。

## 数据模型（SQLite）

- `library_lists`（每次成功上传一个不可变清单版本）、`app_meta`（当前清单版本指针，重启不丢）
- `libraries`（字库+版次+优先级，按清单版本归属）、`glyphs`（字库内字模号→字，按清单版本归属）
- `volumes` / `volume_chars`（册与用字，保留用字顺序）
- `active_matrices`（各册**上次交印**生效的字模，以 glyph_id 固定在对应历史版本上）
- `submit_seq`（全局生效序号）、`orders`（单号、幂等键、指纹、整单 JSON 快照）

## 旧版数据库升级

旧版（`libraries.current` 标记模型）SQLite 库在应用首次打开时自动迁移，无需手工导数据：

- 旧 `current=1` 的字库整体封存为“升级前清单”并置为当前版本，
  **首次成功重传前的交印沿用升级前的选字结果**；`current=0` 的历史字库归档保存；
- 保留原有 `library_id` / `glyph_id` / `volume_id`，已交印册与历史单据原样可查可下载；
- 迁移后 `PRAGMA foreign_key_check` 与 `integrity_check` 均通过。

## 做完了什么 / 验过什么 / 未完成

### 已完成

- FastAPI + SQLite 全量功能：字库/用字上传、优先选库、交印出单、单据重取与 CSV 下载、状态总览、单页网页与样例数据。
- **清单版本化替换流程**：每次成功上传整体存为不可变版本并切换指针；上传失败（坏文件、字模号冲突、保存失败）指针不动，继续上一份清单。
- **新交印只从最近一次成功上传的清单按优先顺序取字**：交印事务开始即锁定清单版本，一笔交印只用一份完整清单；删字后备库顶上、无后备库缺字则 422 拒绝交印。
- **字模号恒定不变量**：同一字库同一版次内字模号→字在所有历史版本中保持一致，冲突即整单拒绝。
- 已交印册与历史单据固定在各自交印时的清单版本，旧增减单原样重取/下载；重启后按最后一次成功上传的清单取字（指针持久化在 SQLite）。
- **旧版 SQLite 库自动升级**：旧 current 模型封存为升级前清单，首次重传前沿用升级前选字结果，ID 与历史数据完整保留。
- 并发串行化（上传/交印共用应用锁 + 数据库立即事务 + WAL + 30s 忙等待）、幂等键与无键判重、缺字/保存失败回滚。
- Dockerfile 与 docker-compose（命名卷持久化、健康检查）。

### 已验证（本环境实际运行）

- `pytest` 17 个用例全部通过：原 10 个用例（含两册先后弃用同一字模、并发 4 册、幂等、回滚）零回归，
  新增 7 个覆盖删字后备库顶替、无后备库缺字拒绝、上传失败沿用上一份、字模号恒定、
  单笔交印只用一份清单、重启持久化、旧库就地升级。
- 真实启动 uvicorn HTTP 冒烟（含一次进程重启）：
  v1 交印取优先库 → 重传 v2 删字后新交印改取后备库且旧字模不再出现、旧单 JSON/CSV 原样可下载 →
  v3 无后备库缺字 422 且沿用原清单无新单 → 坏文件/字模号冲突上传失败指针不动 →
  重启后仍按 v3 取字、历史单据可下载 → v4 上传后按新版本取字。
- 旧版 `data/smoke.db` 副本迁移：`foreign_key_check` 无违规、`integrity_check=ok`、
  4 单/12 active/12 字模完整；空旧库与含 `current=0` 归档库两种边界同样迁移成功。
- 编码回退（UTF-8 BOM / GB18030）、无表头用字表、坏表头 400、未知册/单号 404、保存失败回滚。

### 未完成 / 限制

- 本环境没有 Docker 守护进程，`docker compose up --build` 仅做了文件级准备，未实机构建运行；
  Dockerfile 基于 `python:3.11-slim` 与已验证的依赖版本，逻辑上与本地运行一致。
- 应用级互斥锁只在单进程内生效；多进程/多副本部署时依赖 SQLite 的立即事务与忙等待兜底，
  建议仍以单副本 + 卷持久化方式运行（compose 默认即如此）。
- 没有账号/鉴权与操作审计（题目未要求）；`/api/reset` 仅适用于演示环境。
